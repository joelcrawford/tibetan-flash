# CLAUDE.md

## What this is

A flashcard app for learning Tibetan (and Japanese) vocabulary and texts, with
TTS pronunciation. Ships as a web app (React) and an iOS app (Expo/React
Native) sharing the same deck/reader logic.

## Architecture map

- `apps/web/` — React + TypeScript + Vite frontend (`src/App.tsx`, `Reader.tsx`).
- `apps/ios/` — Expo/React Native app; mirrors the web app's screens, imports
  the same shared logic.
- `shared/` — cross-platform TypeScript: `hooks/useDeck.ts` (card/session
  state), `hooks/settings.ts`, `reader/` (text rendering), `types/types.ts`,
  `languages/<code>/` (per-language module: `sessions.ts`, `glossary.json`,
  `texts/`, `module.ts` — add a language by dropping a module here and
  listing it in `shared/languages/index.ts`).
- `shared/languages/tibetan/dictionary.json` — committed build artifact (ACIP
  dictionary), generated by `scripts/build-gmr-dictionary.mjs` from source
  CSVs that live in the untracked `data/` directory (see below).
- `server/` — small Node/Express server that proxies TTS requests.
- `src/python/` — FastAPI TTS server (`facebook/mms-tts-bod` model).
- `scripts/` — build/ingest/format tooling (`.mjs`) plus their `*.test.mjs`
  tests, run via Node's built-in test runner.
- `docs/` — design notes, mockups, specs; not authoritative, may be stale.

## Dev workflow

- Install: `npm install` (root workspaces cover `apps/web` and `apps/ios`).
- Run web + API server: `npm run dev` (Vite on :5173 + Node server).
- Run the Python TTS server separately (first time creates a venv and
  downloads the model): see README for the `venv`/`pip install` steps, then
  `python src/python/tts_server.py`.
- iOS: `npm run ios:dev` (starts Python, Node, and Expo together).
- Typecheck: `npm run typecheck`.

## Tests

- `npm test` runs `node --test scripts/` — covers `reader.test.mjs`,
  `segment-text.test.mjs`, `gmr-dictionary.test.mjs`.
- `gmr-dictionary.test.mjs` rebuilds `shared/languages/tibetan/dictionary.json`
  from source CSVs and validates it. If the source CSVs in `data/` are absent
  (e.g. a fresh clone, since `data/` is untracked by design — large source
  files, not code), the test instead validates the already-committed artifact.

## Code conventions (observed)

- TypeScript in `shared/` and `apps/web`/`apps/ios`; plain ESM `.mjs`/`.js` in
  `scripts/` and `server/`. Double quotes, semicolons, no trailing commas
  enforced — there is no eslint/prettier config, so just match surrounding
  file style.
- React function components + hooks; Tailwind utility classes for styling
  (classes often assembled as joined string arrays for readability).
- Cross-platform code lives in `shared/` and is imported by relative path from
  both `apps/web` and `apps/ios` — don't fork logic into one app only.
- Comments are sparse and used only to explain non-obvious invariants (e.g.
  migration/dedup logic), not to restate what code does.

## What NOT to touch

- `deploy.sh`, `nginx.conf`, `ecosystem.config.cjs` — production deploy
  machinery. Any change to these must be reviewed by the deploy-guard
  subagent and requires explicit owner approval.
- `data/` is untracked on purpose (large dictionary source CSVs). Don't try
  to add it to git or "fix" its absence — the committed artifact is
  `shared/languages/tibetan/dictionary.json`.
- Merging to `main` deploys web + server to production automatically via
  SSH/rsync/PM2 (per-directory rsync targets). Treat `main` merges as
  production releases.
- iOS builds/submissions are owner-Mac-only — don't attempt `npm run ios:build`
  or `npm run expo` from this environment.

## Standing workflow

- Work on `agent/*` branches only. Never commit or push to `main`.
- Before writing code, create or reference a GitHub issue with acceptance
  criteria (delegate drafting to the spec-writer subagent).
- Branch name: `agent/<issue#>-<slug>`.
- PR body must include `Closes #N`.
